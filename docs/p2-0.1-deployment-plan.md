## 1. 决策已定：A —— 两个栈都钉不可变 SHA

你已选定 **A**。仓库里的 compose 已按此改好并加了回归测试：

| | 之前 | 现在 |
|---|---|---|
| Shadow 镜像 | `…-shadow:shadow-stable`（可变指针） | `…-shadow:sha-${SHADOW_SHA}`（**必填**） |
| Shadow `GIT_SHA` / `IMAGE_TAG` | `${GIT_SHA:-unknown}` / `${IMAGE_TAG:-shadow-stable}` | 均为 `${SHADOW_SHA:?…}` |
| Dashboard 镜像 | `sha-${DASHBOARD_SHA}`（已是钉死） | 不变 |
| Dashboard `GIT_SHA` / `IMAGE_TAG` | `${GIT_SHA:-unknown}` / `${IMAGE_TAG:-dashboard-stable}` | 均为 `${DASHBOARD_SHA:?…}` |

**为什么这一条是必要的**：`shadow-release` 在发布末尾会前移 `shadow-stable`，
它**已经指向 `sha-1d66e4da…`**：

```
shadow-stable -> sha-1d66e4da7bfb8bf44480480d44996743b8901e0d (released as shadow-v0.1.3)
```

生产容器此刻仍跑旧镜像（启动时拉的），但 compose 写的是 `…:shadow-stable`。
**任何一次 `docker compose pull` 或 Unraid 面板"更新"，都会在没人选择的情况下
换到 v0.1.3。** 钉死 SHA 之后这个风险消失。

同时修掉了第二个隐患：两个栈的 `GIT_SHA` / `IMAGE_TAG` 原本会默认成
`unknown` / `*-stable`。这两个字段会写进 `runs` 并发布到心跳，是运维回答
"线上跑的是哪一版"的**唯一**入口——让它报告一个可变指针，等于在最关键的那个
字段上撒谎。现在它们与镜像来自同一个变量，**不可能不一致**。

> 注意：`IMAGE_TAG` 现在携带的是**裸 commit sha**（不含 `sha-` 前缀），
> 因为前缀已由 image 字段写死。例如 `1d66e4da7bfb8bf44480480d44996743b8901e0d`。

新增回归测试（`tests/test_workflows.py`）：Shadow 栈不得出现 `:shadow-stable`、
不得出现 `:latest`、`GIT_SHA`/`IMAGE_TAG` 不得有默认值回退。改动 compose 回退
到旧写法会直接红。

## 3. 停机预计影响

| 服务 | 预计中断 | 影响 | 说明 |
|---|---|---|---|
| **Shadow** | **约 30–90 秒** | 中断期间**不产生新决策** | `stop_grace_period: 60s`；正常 SIGTERM 会走 `finish_run`，把 `status` / `stopped_at` 写进 `shadow_runs` |
| **Dashboard** | 约 5–15 秒 | 页面短暂不可用 | 纯只读旁路，**不影响采集** |
| **Collector** | **0 秒** | 无 | **本轮完全不碰 Collector** |

**采集不会中断**：Collector 与 Shadow 归档是两个进程、两个镜像、两个数据库。
Shadow 停机期间 Collector 照常写 JSONL 归档；Shadow 重启后从 checkpoint
续读（v0.1.2 的修复保证这一点），**不会重复消费、不会漏读**。

**重启的统计后果**（这是唯一需要你知道的"损失"）：
心跳里的 `cycles` / `uptime_seconds` 会从零开始。
决策计数**不会**——它们统计的是整个 shadow 数据库，重启只增不减
（`docs/dashboard-data-contract.md` §4.1 有三条证据）。

## 5. 回滚操作

回滚 = **把变量改回旧 SHA，再点一次 Apply**。不需要拉新镜像、不需要动数据库。

### 5.1 Shadow 回滚

在 Compose Manager Plus 的 Shadow 栈里，把变量改回：

```
SHADOW_SHA=b60bbd86af6ee5f86e9f08ef4ff92b6a9129ade8
```

然后 **Apply**（它会重建容器并 `docker compose pull` 该 `sha-b60bbd86…` 镜像）。

等价的命令行（如果你更习惯直接在终端做）：

```bash
cd /mnt/user/appdata <你的 compose 目录>
# .env: SHADOW_SHA=b60bbd86af6ee5f86e9f08ef4ff92b6a9129ade8
docker compose -p weatherquant-shadow up -d
```

- 数据库**无需回滚**（本轮没有迁移，新旧镜像面对同一份 schema）；
- 若同时需要回退**数据**，先按 §4.2 恢复备份，再起容器；
- 新版写出的 `*-snapshot.json` 会留在 `reports/`，旧版 Shadow 不再更新它们，
  Dashboard 会在 `stale_after_seconds` 后**如实显示 stale**——设计内降级，无害；
- **不影响 Collector**（两个镜像、两个 tag 命名空间、两个数据目录）。

### 5.2 Dashboard 回滚

```
DASHBOARD_SHA=dc28ae74cf4e5925883ba1e679e7919f7f482ad0
```

然后 **Apply**。

### 5.3 回滚判据

出现下列任一情况即回滚，**不需要先诊断完**：

1. Shadow 非 `healthy`，或 `fatal_error` 非空；
2. `liveness.collector_last_seen` 冻结 > 5 分钟（checkpoint 又出问题的签名）；
3. `data_quality.errors` 持续增长；
4. 周期耗时显著恶化（对比部署前 `duration_ms`）；
5. 决策计数停止增长且 Collector 仍在采集。

回滚后：**保留备份、保留证据、记录日志**，不要清库、不要重跑。

### 6.7 checkpoint 恢复（**最重要**）

| # | 标准 | 判据 |
|---|---|---|
| G0 | **先量出停机期新增归档** | 停机前记下 `raw/rest/<当日>.jsonl` 的行数 N₀；起容器后记 N₁。**预期首周期读取量 ≈ N₁ − N₀**（见下方说明） |
| G1 | **首周期读取量与新增归档相符** | 首周期 `lines_read` **≈ N₁ − N₀**，不是"接近 0"，也**不是整段归档的行数** |
| G2 | 第二周期起归零 | 第 2、3 周期 `lines_read` 接近 0（只吃增量）。**持续为高位 = 重复消费** |
| G3 | 场地时间戳不冻结 | 重启后 `latest_orderbook_venue_utc` 恢复前进 |
| G4 | 无跨天缺口 | `data_quality.data_gaps` 不因重启而增加 |
| G5 | 无 `STALE_ORDERBOOK` 风暴 | 重启后周期内 `STALE_ORDERBOOK` 占比不显著高于重启前 |

**G1 为什么不是"接近 0"**：Shadow 停机的 30–90 秒里 Collector **照常写归档**。
所以重启后第一个周期读到的行数，正确值是**停机期间真实新增的那些行**，不是 0。
判据是**"读到的 ≈ 新增的"**，而不是"读到的少"。

**怎么区分"正常新增"与"重复消费"**：

| 现象 | 结论 |
|---|---|
| 首周期 ≈ N₁−N₀，之后归零 | ✅ 正常 |
| 首周期 ≈ 整个归档文件的行数 | ❌ 从字节 0 重读（checkpoint 未生效） |
| 第 2、3 周期仍持续高位 | ❌ 重复消费 |
| 首周期 ≫ N₁−N₀ | ❌ 越过 checkpoint 重读了已提交的行 |

若停机很短、N₁−N₀ 为 0，首周期 `lines_read = 0` 同样是**正常**——
请按 G0 实测的差值判断，不要套用任何固定数字。

### 步骤 1 · 停 Shadow 并备份数据库

> **必须先停再复制**：Shadow 对 `.duckdb` 持独占租约，运行中复制会得到不完整文件。
> 正常 `stop` 还会让引擎写下 `finish_run`（`status` / `stopped_at`）。

**Compose Manager Plus**：Shadow 栈 → Actions → **Stop**。

等容器完全停止后：

```bash
mkdir -p /mnt/user/appdata/weatherquant-shadow/backups
ts=$(date -u +%Y%m%dT%H%M%SZ)
SRC=/mnt/user/appdata/weatherquant-shadow/shadow
BAK=/mnt/user/appdata/weatherquant-shadow/backups

cp ${SRC}/shadow.duckdb ${BAK}/shadow-${ts}.duckdb
# WAL 必须一并复制，否则恢复后会缺最后一段未合并的写入
[ -f ${SRC}/shadow.duckdb.wal ] && cp ${SRC}/shadow.duckdb.wal ${BAK}/shadow-${ts}.duckdb.wal

ls -la ${BAK}/shadow-${ts}*
sha256sum ${BAK}/shadow-${ts}.duckdb
```

**确认备份存在且非零大小**再进行下一步。把 `${ts}` 记下来。
