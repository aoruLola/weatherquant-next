## ⚠️ 1. 首先要知道的一件事：`shadow-stable` 已经移动了

`shadow-release` 在发布末尾会把 `shadow-stable` 指针移到新镜像。它**已经指向
`sha-1d66e4da…`** 了，日志：

```
shadow-stable -> sha-1d66e4da7bfb8bf44480480d44996743b8901e0d (released as shadow-v0.1.3)
```

**含义**：生产容器此刻仍在跑旧镜像（它启动时拉的是当时的 `shadow-stable`），
但 compose 写的是 `image: …:shadow-stable`。所以**任何一次 `docker compose pull`、
或 Unraid 面板的"检查更新 / 更新容器"，都会在你没有明确选择版本的情况下换到
v0.1.3**。

这与 Dashboard 不同——Dashboard 的 compose 用
`sha-${DASHBOARD_SHA}` 钉死，必须显式改 `.env` 才会动。

**因此建议（择一，你定）**：

- **A（推荐）**：确认本计划后，我给出的步骤里把 Shadow 镜像**显式钉到
  `sha-1d66e4da…`**，而不是靠 `shadow-stable`，让"拉哪个版本"成为一次显式决定；
- **B**：接受 `shadow-stable` 即"最新已验证版本"的语义，按现状部署。
  但要清楚：今后每次 shadow 发布都会自动前移这个指针。

在你选定之前，**请不要在 NAS 上点"更新"**。

## 3. 停机预计影响

| 服务 | 预计中断 | 影响 | 说明 |
|---|---|---|---|
| **Shadow** | **约 30–90 秒** | 中断期间**不产生新决策** | `stop_grace_period: 60s`；正常 SIGTERM 会走 `finish_run`，把 `status` / `stopped_at` 写进 `shadow_runs` |
| **Dashboard** | 约 5–15 秒 | 页面短暂不可用 | 纯只读旁路，**不影响采集** |
| **Collector** | **0 秒** | 无 | **本轮完全不碰 Collector** |

**采集不会中断**：Collector 与 Shadow 归档是两个进程、两个镜像、两个数据库。
Shadow 停机期间 Collector 照常写 JSONL 归档；Shadow 重启后从 checkpoint
续读（v0.1.2 的修复保证这一点），**不会重复消费、不会漏读**。

**重启的统计后果**（这是唯一需要你知道的"损失"）：
心跳里的 `cycles` / `uptime_seconds` 会从零开始。
决策计数**不会**——它们统计的是整个 shadow 数据库，重启只增不减
（`docs/dashboard-data-contract.md` §4.1 有三条证据）。

## 4. 数据库备份与恢复

沿用 `docs/shadow-unraid-deployment.md` §9 的既有约定。
**必须先停容器再复制**——Shadow 进程对 `.duckdb` 持独占租约，
运行中复制会拿到不完整文件。

### 4.1 部署前：记录 + 备份

```bash
# 镜像版本与 checkpoint 状态

ls -la /mnt/user/appdata/weatherquant-shadow/shadow/
```

**2026-10-13 02:2x UTC 的实读基线**（供对照；执行时请重新读一次）：

| 指标 | 值 |
|---|---|
| Shadow 运行 | `cycles=4408`，`uptime=34,689s`，`started=2026-10-12T16:29:10Z`，`mode=LIVE` |
| evaluated | 442,574 |
| ACCEPT / REJECT / NO_TRADE | 45,996 / 283,564 / 94,644 |
| **DATA_UNAVAILABLE** | **18,370**（与 10-12 18:12 实读**完全相同**，仍属待调查项） |
| Collector DB / 原始归档 | 2,398,105,600 B / 3,046,825,892 B |

| Collector | `app_version=0.1.0`，`telemetry={}`（按指示不升级） |

**再备份（停机窗口内）**：

```bash
docker stop weatherquant-shadow          # 优雅停止，写入 finish_run
mkdir -p /mnt/user/appdata/weatherquant-shadow/backups
ts=$(date -u +%Y%m%dT%H%M%SZ)
cp /mnt/user/appdata/weatherquant-shadow/shadow/shadow.duckdb \
   /mnt/user/appdata/weatherquant-shadow/backups/shadow-${ts}.duckdb
# 若存在 WAL 一并复制，否则恢复后会缺最后一段未合并的写入
[ -f /mnt/user/appdata/weatherquant-shadow/shadow/shadow.duckdb.wal ] && \
cp /mnt/user/appdata/weatherquant-shadow/shadow/shadow.duckdb.wal \
   /mnt/user/appdata/weatherquant-shadow/backups/shadow-${ts}.duckdb.wal
ls -la /mnt/user/appdata/weatherquant-shadow/backups/shadow-${ts}*
```

> **WAL 说明**：`db_bytes` 只统计主文件（与 Collector 口径一致），
> 但**备份必须连 `.wal` 一起复制**，否则恢复后会丢掉尚未 checkpoint 的写入。

### 4.2 恢复（任一需要回退数据的场景）

```bash
docker stop weatherquant-shadow
cp /mnt/user/appdata/weatherquant-shadow/backups/shadow-<TS>.duckdb \
   /mnt/user/appdata/weatherquant-shadow/shadow/shadow.duckdb
cp /mnt/user/appdata/weatherquant-shadow/backups/shadow-<TS>.duckdb.wal \
   /mnt/user/appdata/weatherquant-shadow/shadow/shadow.duckdb.wal   # 若有

```

**本轮预计不需要恢复**：没有 schema 迁移、没有数据改写。备份是纪律，不是预感。

## 5. 回滚操作

### 5.1 Shadow 回滚

```bash
# compose 改回不可变回滚目标（不是 shadow-stable）
# image: ghcr.io/aorulola/weatherquant-next-shadow:sha-b60bbd86af6ee5f86e9f08ef4ff92b6a9129ade8
docker compose -f docker/compose.shadow.unraid.yaml up -d
```

- 数据库**无需回滚**（无迁移）；
- 新版本写出的 `*-snapshot.json` 会留在 `reports/`，旧版 Shadow 不再更新它们，
  Dashboard 会在 `stale_after_seconds` 后**如实显示 stale**——设计内降级，无害；
- **不影响 Collector**（两个镜像、两个 tag 命名空间）。

### 5.2 Dashboard 回滚

```bash
# stack .env: DASHBOARD_SHA=dc28ae74cf4e5925883ba1e679e7919f7f482ad0
docker compose -f docker/compose.dashboard.unraid.yaml up -d
```

### 5.3 回滚判据

出现下列任一情况即回滚，**不需要先诊断完**：

1. Shadow 非 `healthy`，或 `fatal_error` 非空；
2. `liveness.collector_last_seen` 冻结 > 5 分钟（checkpoint 又出问题的签名）；
3. `data_quality.errors` 持续增长；
4. 周期耗时显著恶化（对比部署前 `duration_ms`）；
5. 决策计数停止增长且 Collector 仍在采集。

回滚后：**保留备份、保留证据、记录日志**，不要清库、不要重跑。
