| **Shadow** | ①接入 `publish_detail_snapshots`；②心跳新增 `app_version`/`image_tag`/`db_bytes`；③`books_total` 修正 | 用含本轮提交的源码重建 `Dockerfile.shadow` 并替换容器 | Model vs Market、决策行明细、温度桶分布继续显示 `unavailable` + 原因；Shadow DB / 版本显示 `暂未接入`。**采集与决策不受影响** |
| **Dashboard** | 过期市场标注、ACCEPT 独立度、Shadow 版本与 DB 显示 | 重建 `Dockerfile.dashboard` 并替换容器 | 继续按旧版渲染；新增字段被后端忽略 |

Collector **本轮零改动**（`archive_records` 的修复被刻意留在 Collector 之外，见 §6.2-#4）。

### 7.2 影响范围

- **不会中断采集**：Dashboard 与 Shadow 明细快照都是**只读旁路**；快照失败按设计
  只记一条 warning 质量事件，引擎继续跑。
- **重启不清零决策计数**：`evaluated` / `accept_scope` 等统计的是整个 shadow
  数据库，重启只是新增一行 run（§4.1）。唯一归零的是心跳里的 `cycles` 与
  `uptime_seconds`。**本报告初版这里写反了**，已在 §1.3、§6.2-#3、
  `research/p2-0.1-soak.md` 一并更正。
  部署前仍然建议留档当前快照——理由不是“怕它消失”，而是为了对照新版本上线后
  计数是否仍单调前进。
- **不会触碰**：`shadow-thresholds.json`、模型工件、collector 归档、两个 DuckDB 文件。

### 7.3 回滚

1. `docker compose -f docker/compose.shadow.unraid.yaml ... ` 换回上一个镜像标签
   （当前生产为 `shadow-v0.1.2`，对应 `b60bbd8`）；Dashboard 同理回到 `dashboard-v0.1.0`。
2. GHCR 上的 `sha-<commit>` 标签**只增不改**，旧镜像始终可拉取；`shadow-stable` /
   `dashboard-stable` 未被本轮移动（发布由标签触发，未打标签即不会发布）。
3. 回滚后 Dashboard 自动退回 `unavailable + 原因`，不需要回滚数据库或配置。
4. **数据无需回滚**：本轮没有任何 schema 迁移，也没有任何写入生产库的操作。

### 7.4 部署前请确认

- 是否**现在**部署（Shadow 重启会清零当前运行口径的累计数），还是等 7 天观察开始时一起做；
- 是否批准同时把 Collector 升到 v0.1.2（才能拿到 WS 队列指标，§6.2-#2）。

## 8. 后续 7 天数据观察计划

**目标**：攒出一批**完整、可信、可追溯**的实时样本，为之后的模型评估与模拟交易
研究提供地基。**成功标准不是 ACCEPT 变多，而是没有未解释的数据洞。**

### 8.1 每日只读检查（约 5 分钟，全部走 `http://192.168.10.168:8787`）

| 检查 | 端点 | 判据 |
|---|---|---|
| 三源新鲜度 | `/healthz` | `collector/shadow/shadow_report` 全为 `fresh` |
| 采集是否断流 | `/api/v1/shadow/report` → `liveness` | `collector_silence_seconds` 不长期 > 900；`latest_orderbook_venue_age_seconds` 持续前进（**不前进= checkpoint 又坏了**） |
| 数据质量 | `/api/v1/shadow/report` → `data_quality` | `data_gaps`、`errors` 不增长；新增 `by_kind` 必须能解释 |
| 决策健康 | `/api/v1/decisions` | `DATA_UNAVAILABLE` 占比不持续上升；REPLAY 只在回放时出现 |
| 磁盘 | `/api/v1/system` → `storage` | `disk_free_percent` 不跌破 30% |
| 独立度 | `decisions.accept_scope` | `accepted_distinct_markets` 与观测数的比值被记录下来（这是之后所有 ACCEPT 统计的分母） |

每次把结果追加进 `research/p2-0.1-soak.md`（表格：日期 / 关键数字 / 异常 / 处置）。
**发现异常：先记录证据、再定位原因，不允许清库、放宽阈值或隐藏异常。**

### 8.2 累计口径

当前所有决策计数都是**当前运行**口径，Shadow 每重启一次就归零。观察期内：

- **每次重启都记一行**（时刻、原因、重启前的最终 `evaluated` / `accept_scope`）；
- 任何跨天结论都必须写明“含 N 次重启”，或者只用**单次连续运行**内的子样本；
- 在实现跨重启累计口径之前，**不要**把多段运行的 ACCEPT 直接相加当成“7 天累计”。

### 8.3 观察期内禁止

真实下单、钱包 / 私钥、自动交易、修改阈值或模型参数、清库 / 重建、伪造历史数据、
在生产环境跑破坏性测试。**为测试便利而重启生产容器同样算中断采集，需要单独批准。**

### 8.4 退出条件

连续 7 天：无未解释的数据洞、无 checkpoint 停滞、无容器非预期重启，
且 `accept_scope` 已积累到可支撑“独立市场 × 目标日”级别的样本量。
满足后才讨论模型评估与模拟交易阶段（P2 的前提“模型样本外有效”**仍未满足**，
见 `research/baseline-comparison.md`——本轮工作不会让模型变好，只会让数据可信）。

## 9. 结论

- **采集链路健康且未中断**：REST / WS / 归档 / checkpoint 推进在生产上均可证，
  磁盘 91.9% 充裕，数据质量事件为 0。
- **Dashboard 骨架完整**，任务 3.5 指定的 Model vs Market 与另外两块明细原本
  **结构性缺席**——根因单一（契约 §4 未接入），本轮已在代码层接上，并且接入过程
  **当场抓到生产者 SQL 与真实 schema 不符**这一缺陷（只存在于测试自造的表里）。
- **统计口径**：旧快照漏记 `DATA_UNAVAILABLE`（18,370，占 12.5%）这一事实已记录；
  ACCEPT 的独立度维度（独立市场 / Token / 重复周期）本轮补齐，
  过期市场不再与当前市场混在首屏。
- **仍为红的只有一件事**：主干 `ci` 的间歇性挂起。已加 `faulthandler_timeout`
  让它下次自己说出卡在哪个用例，但**定位与修复必须在交付前完成**。
- **生产未被触碰**：所有改动要在生产生效都需要重建镜像并重启容器，
  影响范围与回滚见 §7，等你批准。
